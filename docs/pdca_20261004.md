# 議論と実測を繰り返すPDCA

`pdca`は、複数人格の独立提案、相互案の批評と選定、実験実行、測定結果の反省を繰り返す。
次のラウンドには、採用中の案に加えて、直近の失敗案・測定値・批評・反省が渡る。
初期案も先に実測するため、モデルが自分で付けた点数を改善の根拠にしない。
候補中の命令文は編集対象のデータと明示し、測定済み候補をそのまま返した場合は
一度だけ再提案させる。理由文だけの変更を新しい候補として測定しない。

関連する研究は[BAAIのAREX-2](https://huggingface.co/BAAI/AREX-2)で、
Qwen3.8-27Bを基に、テスト時の提案・測定・反省・修正を反復する能力を学習したもの。
本実装は既存のOllamaモデルへ同種の実行ループを接続する。
更新するのはタスクで定義した候補のプロンプト・設定であり、重みの勾配更新はこのコマンドには含まない。

## 実行

Ollamaに`qwen3.5:4b`がある環境で、リポジトリ直下から実行する。

```sh
python3.11 cod_model.py pdca \
  --task configs/pdca-general-body.json \
  --out runs/pdca-body-001 \
  --model qwen3.5:4b --min-rounds 2 --max-rounds 3
```

同梱タスクは、現在のCoD本文system promptを初期案にし、
Ollamaで実際に本文を生成して既存の`score_output`で測定する。
開発用8問が議論へ渡り、別topicの最終検証8問は候補確定後にだけ測定する。
最終検証の結果を読んだ後の提案・反省は実行しない。

`--model`は議論側のモデルで、測定対象のモデルはタスクの`experiment.argv`で指定する。
この例は両方ともQwen3.5-4B。手元のQwen3.8等のモデル名へ議論側を切り替えることもできる。
その場合も、測定対象やコーパスが自動で変わるわけではない。

Generalは既定で8人格。`--personas`に2人以上のIDを指定すれば参加者を選べる。
タスクの`domain`は`general`・`software`・`weather`から選び、それぞれの既存人格を使う。
賛成役・反対役への固定はせず、同じ候補を支持する複数の理由も保存する。
同じ候補の重複測定は避けるが、支持人数を採用スコアに加算しない。

各ラウンドは全人格の独立提案、1人の批評・選定、1件の実験、別人格の反省で構成する。
批評役・反省役はラウンドごとに交代する。全員分の独立モデル呼び出しがあるため、
人数・生成長・モデル速度に応じて時間がかかる。
`--num-predict`と`--timeout`は正の整数。ラウンド数は`1 <= min <= max <= 20`。
目標へ届いても`min-rounds`までは議論し、上限で終了する。
説明欄は提案220字・批評260字・観測220字・次の変更180字まで。
詳細履歴は保存し、モデルには必要な測定・失敗・直近の反省を渡す。

## 測定と採用

初期測定は`M000`、以降は`M001`等のIDを持つ。
提案・批評・反省は最新測定IDの引用が必須で、未知IDや古いIDだけの引用を拒否する。
モデルの説明は仮説・提案として保存する。引用IDが正しくても自然文の解釈まで正しいとは限らず、
測定値そのものは実験プロセスのJSONだけから取得する。

採用順序は`passed_then_score`。

1. 正常に測定できた案を、測定エラーの案より優先する。
2. `passed=true`を`false`より優先する。
3. 同じ合否なら高いスコアを優先し、同点なら現在案を保つ。

これにより、制約を破って得点だけ上げた案が合格済みの案を置き換えることを防ぐ。
`score`は大きいほど良い値。時間や誤差を最小化したい実験では、実験側で負数等へ変換する。
構文不正、非有限数、非ゼロ終了、タイムアウトは測定エラーとして保存し、架空の点数を補わない。

`result.json`の`status`と`development_improved`は開発測定の結果。
最終検証は`holdout.nonregression`・`holdout.supported_improvement`とH000/H001の合否で別に確認する。
開発側の`improved`だけを一般性能の向上と扱わない。
`best_candidate.json`は今回の実験内の採用案で、既定設定・本番Weightの自動置換はしない。

## 他プロジェクトの実験へ接続

タスクJSONには目的、初期候補、候補schema、実験コマンドを指定する。
`project_root`はタスクファイルの親ディレクトリを基準に解決する。
モデルが変更できるのは`candidate_schema`に列挙した値だけ。
現在のschemaは浅いobjectのstring/number/integer/boolean、必須キー、enum、長さ・数値範囲を扱う。
未知キー・未対応schemaを拒否する。

`experiment.argv`は事前に指定した固定コマンド配列を、shellを介さず実行する。
そのプロセスにはstdinで次の形を渡す。

```json
{
  "candidate": {"system_prompt": "今回試す案"},
  "output_dir": "/absolute/run/measurements/M001",
  "phase": "development"
}
```

実験プロセスはstdoutへ1個のJSONを返す。以下の数値は形式例である。

```json
{
  "schema_version": 1,
  "score": 0.75,
  "passed": false,
  "metrics": {"direct_valid": 6, "total": 8},
  "failures": [{"case": "case_03", "reason": "条件が欠落"}],
  "artifacts": ["raw.json"]
}
```

詳細ログは`output_dir`内へ保存し、実在するファイルを`artifacts`へ列挙する。
stderrは診断用に保存する。`holdout`を指定する場合は同じ形式の固定コマンドを用意し、
`phase=holdout`を受けて最終検証を行う。実験コマンドはプロジェクトで管理する測定器であり、
モデルの提案文をそのままシェルコマンドとして実行する機能ではない。

## 保存・中断・検証範囲

`journal.json`に各段階を原子的に保存し、完了時に`result.json`と`best_candidate.json`を出力する。
`measurements/<ID>/`には入力、stdout、stderr、測定結果、実験固有のrawが入る。
提案・批評・反省のJSONと原文、生成設定、seed、タスクと実装のSHAも記録する。
同じ出力ディレクトリの上書きは拒否する。

タイムアウト・中断時は、この実験が起動したプロセス群を停止して記録する。
途中記録は調査用に読めるが、途中再開機能はまだない。再試行は別の出力先を使う。

容量監視は既定20GiB・2秒間隔で、作業先・出力先・OSの一時領域を確認する。
`--min-free-gib`と`--resource-check-seconds`で指定できる。
容量不足を検知すると自身の処理を中断し、他のアプリやOllamaサーバー全体を終了させない。
実験プロセスの停止はOS全体のメモリ・容量を保証するものではなく、再開前に空き容量も確認する。
容量監視は専用プロセスのCLIで利用する。バックグラウンドthreadからの呼び出しは、
同じプロセス内の別処理へ割込みを送らないよう開始前に拒否する。
容量停止は終了コード2・`resource_stopped`として記録し、通常の改善なしと区別する。
Ctrl-C時の進捗は`journal.json`に残る。OS全体やOllamaサーバーを終了する機能ではない。

同梱の本文評価は、小規模な合成事例と既存の文字列・時制・根拠検査による測定である。
自然文の意味保持の完全な証明ではない。得点と原文を確認し、改善案は別の未学習事例や
実際のCoD討論でも評価する。従来の`rsi-shadow`は保存済みrunの比較に引き続き使える。

## 実モデル実行の記録

2026-10-04の8人格・3ラウンドでは、開発用の直接合格が初期3/8、候補は3/8・3/8・2/8となり、
初期案を保持した。最新測定を参照した修正版の生成と実験は自動で実行されたが、改善は得られなかった。
反省には「しません」を完了形と解釈する誤り等があり、固定表現検査の不一致箇所を明示する改善を用意した。

20:41にホストが再起動し、最終検証H000は5件のrawを保存したところで中断した。
H000の残りとH001は未完了で、最終検証成功とは扱わない。
kernelには20:34〜20:40の`low swap: failed to create swapfile`が残っていた。
どのプロセスが容量・メモリ増加の主因かは特定していない。
再起動後に容量監視を追加してCPUテストで確認し、空き容量・メモリを確認してから再検証した。

ログは`/Volumes/data4/cod_model_weight/evaluations/pdca-general-body_20261004/run01`に残し、
旧sourceとrawを保持して`interruption.json`に観測した中断状態を追記した。
古いjournalの`running`は再起動前の値であり、プロセス生存の根拠にはしない。

| 実行 | 議論役・人数 | 開発測定 | 最終検証 | 結果 |
|---|---|---|---|---|
| run01 | Qwen3.5・8人 | 初期3/8、候補3/8・3/8・2/8 | H000の5件まで保存 | ホスト再起動で中断 |
| run02 | Qwen3.5・4人 | 初期3/8、候補2/8。重複候補は測定省略 | 初期・維持案とも4/8 | 394.079秒で完走、改善なし |
| run03 | Qwen3.5・4人 | 初期3/8、候補3/8。次ラウンドの修正版生成まで進行 | 未実施 | 容量ガードで停止 |
| run04_qwen38 | Qwen3.8-27B・4人 | 初期3/8。4件の変更案を生成 | 未実施 | 批評中に容量ガードで停止 |

run02の開発・最終検証rawは再採点して元スコアと一致した。
候補SHA、最新測定IDの引用、最終検証の入力が議論へ入っていないこと、
`best_candidate.json`が最終検証前に確定していることも確認した。
引用IDの一致だけでは説明文の正しさを保証しない。4Bの説明には文法解釈や件数の誤りもあった。

run03は内蔵の空き19.8507GiBを21:21:21 JSTに検出し、終了コード2で停止した。
同時刻のOllamaログにも、約5.575秒の要求終了、`cancel task`、`stop processing`が記録された。
これは実要求での中断確認であり、OS全体のメモリ圧迫を防げるという保証ではない。
停止後はこの試験のモデルを解放した。

内蔵に置いていた本作業専用のMLXキャッシュ3,061,129,077 bytesは、
10ファイル全てを元モデルと照合してから
`/Volumes/data4/cod_model_weight/cache_archive/mp-cod-qwen35-v2.OTLCFD`へ退避した。
退避先でも全SHA一致を確認し、内蔵の空きは約23GiBになった。
元モデルは`/Volumes/data4/cod_model_weight/models/Qwen3.5-4B-4bit`に残る。
旧ログの内部キャッシュpathは履歴情報であり、再現には元モデルまたは退避先を使う。

記録は同じaudit rootの`replay_audit_runs02_03.json`、`cache_archive_manifest.json`、
各runの`source_snapshot`で追える。本文評価には採点器のSHAと各入力のseedも保存する。
採点後にアンカーを緩めて合格へ変更していない。

run04では手元の`hf.co/unsloth/Qwen3.8-27B-GGUF:UD-Q2_K_XL`を議論役に使った。
測定対象は同じQwen3.5-4Bで、AREX-2のWeightを導入した試験ではない。
4件の変更案は生成されたが、批評中の21:53:12 JSTに空き19.6122GiBを検出して停止した。
その後この試験のモデルを解放した。提案の有効性を測定できたとは扱わない。

自律提案・批評・実測・反省・修正の接続は実モデルで確認できた。
一方、現行版で修正版を複数回測定して最終検証まで完走する確認は残っている。
性能向上、既定設定への昇格、LoRA Weight完成も未確認。
容量ガードを緩めて再試行せず、追加の容量確保と負荷の見直し後に続ける。
