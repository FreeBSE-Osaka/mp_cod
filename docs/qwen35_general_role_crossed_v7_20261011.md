# Generalの役割を交差させた教材と学習監視の修正

2026年10月11日、Qwen3.5-4Bの全文発言LoRAを、1,088入力の研究教材で再試行する。狙いは、演者や主張番号に発話行為を結び付けず、同じ演者でも提案、同意、対案などを使い分けることにある。前回の学習は80ステップの報告後に監視処理が停止させ、Weightを保存していない。今回も研究HOLDで、学習完了と発言品質は別に確認する。

## 役割と発話行為を交差させる

v6の448学習入力をバイト単位で保持し、学習用10テーマについて、8演者と8発話行為をすべて組み合わせた640入力を追加した。合計は1,088入力、各演者と発話行為の組は17表現となる。追加文は既存の資料付き編集教材を再利用しており、新たな独立教師生成640件ではない。

追加部分では、同じテーマの発話IDを共通にした。IDだけから発話行為を判断する手掛かりを減らすためである。提案と同意を比較する80組では、演者、主張、根拠とIDを揃える。ただし対象主張、phase、前の選択等は発話行為に対応するため、発話行為の指示だけを変更した因果実験ではない。

開発評価48入力と最終評価72入力はv6とバイト単位で同じで、教材へ混ぜていない。実Tokenizerと標準batch iteratorによるCPU監査では、最大758 tokens、教師62,449 tokens、全1,088入力のEOSと末尾改行を保持する。未使用paddingを含む教師位置の末尾幅は最大147 tokensで、固定した末尾160-token投影に収まる。1,088ステップを消費する前に、全教材の学習完了とはしない。

## 前回の停止原因

10月7日の16ステップ試験は保存とプロセス終了まで正常に完了した。教師914 tokens、所要281.813秒、OSの観測physical footprintピーク約11.42GiBで、本学習の起動条件18GiB以下を満たした。

本学習は80ステップまで4,529教師tokensを報告した後、`/usr/bin/footprint`の呼び出しが5秒を超えた。外側の監視処理が例外を受けて学習プロセスを停止し、終了コードは-15、観測メモリピークは約11.51GiBだった。記録された停止理由はメモリ上限超過や空き容量不足ではなく、計測のタイムアウトである。原因不明のクラッシュや学習完了として扱わない。

停止したプロセスが存在しないことと、出力に`adapter_config.json`しかないことを確認した。古いjob journalの`running`表示はプロセスの生存証明ではない。元ログ、設定、評価計画はそのまま保存する。

## macOSの標準APIによる監視

新しい`tools/macos_process_memory.py`は、公開SDKの`rusage_info_v4`に合わせ、`proc_pid_rusage`で現在のphysical footprintと生涯ピークを読む。Pythonの標準ライブラリだけを使い、診断コマンドの起動と文字列解析をなくした。RSSやMLX allocatorの値をphysical footprintの代わりにはしない。

最初の再試行はSHA確認中、現在値とピークの大小関係を含む検査で3回連続して計測を拒否し、146.696秒で安全停止した。学習報告やWeight保存はない。Appleの公開実装ではピークを先に読み、現在値を後で集めるため、二つは同時刻の値とは限らない。大小関係だけで失敗にせず、生の二値を保存し、上限と観測ピークには両者の最大値を使うよう修正した。APIエラーと値の欠落は引き続き拒否する。[Appleの実装](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_resource.c)

一時的な計測失敗は記録して2秒間隔で再計測する。3回連続で失敗した場合は安全停止し、値が取れないまま学習を続けない。現在値または生涯ピークが20GiBを超えた場合は即座に停止処理へ進む。内蔵と外付けの空き容量20GiBを守る既存の監視も維持する。停止対象はこの試行が起動した学習プロセスだけで、他アプリやOS全体の設定は変更しない。

ローカルの175単体テストと、実際のランナーの監視ループへの故障注入5テストが通過した。故障注入は、一時失敗からの回復、連続失敗、計測中のプロセス終了、現在値と生涯ピークの上限超過、成功後の失敗回数リセットを確認する。現在値21GiB、先に読んだピーク19GiBでも上限超過で停止し、観測ピークへ21GiBを残す。学習品質の検査ではない。

96MiBを確保した実プロセスでは、新APIと従来の`footprint`が2MiB以内で一致した。12回の新API計測は最大約0.61ms、1回の従来計測は約60msだった。このCPUプロセスでの計測比較を、MLX学習全体の高速化や長時間安定性の保証にはしない。

## 再試行と評価の条件

新しい試行は元の親Adapterから開始する。停止時の80ステップに対応するWeightがないため、途中再開ではない。Base、親、学習データ、学習率、seed、学習loss、padding、末尾投影、コンパイル無効化は、10月7日に固定した条件を維持する。再試行用の出力名を分け、監視の修正と元の学習計画のSHAを記録する。

保存候補は272、544、816、1,088ステップで固定する。学習と外側の監視の正常終了、全62,449教師tokensの消費、Weightと入力のSHAを確認してから、同じ開発48入力で4候補を比較する。最終72入力は候補選びに使わない。

候補選定は、Baseの合格を失う数、親の合格を失う数、固定事実検査、直接検査、早いステップの順とする。次の評価へ進むには、Baseと親の個別合格を失わず、固定事実検査が親の25/48を上回り、対案と異議の直接検査がそれぞれ4/6以上であることを要する。さらに原文の意味と自然さを点検する。

その後も旧評価18入力と資料付き16入力の実生成、保存原文の再採点での後退確認、Adapter除去後の検査、8人の対照実討論、根拠のある見解変更と独立した理由を確認する。形式やlossが良いだけでは採用しない。既定Weightの置換、Weight公開、dots実接続は行っていない。
